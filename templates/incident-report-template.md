# Incident Report — <title>

| Field | Value |
|---|---|
| Incident ID | INC-<lab>-<n> |
| Severity | SEV1 / SEV2 / SEV3 (justify in one line) |
| Detected | <time, how: alert / customer / you> |
| Resolved | <time> |
| Duration / TTR | <minutes> |
| Author | <you> |

## 1. Impact
Who/what was affected, for how long, how bad. Numbers, not adjectives.

## 2. Timeline (timestamps)
| Time | Event / action | Evidence (command + output snippet) |
|---|---|---|

## 3. Root cause
Technical cause. Then the *contributing* causes (why was it possible?). Use 5-Whys until you hit a process/design gap.

## 4. Resolution
What you changed to restore service. Exact commands/diff.

## 5. What went well / what went badly
Detection speed, tooling gaps, wasted time (be honest: where did YOU lose time?).

## 6. Next steps
| # | Action | Type (prevent / detect / mitigate) | Owner | Due |
|---|---|---|---|---|
Rules: every action must be specific and verifiable. "Be more careful" is not an action.

## 7. Lessons / interview soundbite
Two sentences you could say in an interview about this incident.
